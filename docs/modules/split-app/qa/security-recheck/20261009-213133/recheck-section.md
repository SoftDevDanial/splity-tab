#### SEC-04: A held Enter on Remove of the only item adds a blank item (key auto-repeat after R34 moves focus to Add item)
- **Severity:** LOW. **File:** `src/main.js:110` (`if (bill.items.length === 0) items.focusAdd();`, R34), `src/ui/items.js:78-81` (`focusAdd`), `src/ui/items.js:27` (Remove handler) and `src/ui/items.js:40` (`add.addEventListener("click", onAdd)`). **Boundary:** keyboard auto-repeat. Entry `button.icon-btn[aria-label="Remove {item}"]` of the only item, then focus moves to `Add item`, then each repeat of the held key presses the control that now has focus, sink `addItem` and `saveDraft`.
- **Maps to spec threat:** NEW. The threat-model row for a repeated press names pointer gestures only, and the guard treats a key click (`detail` 0) as a press of its own on purpose, so it cannot see an auto-repeat. It is not a regression of this fix: the tree before the fixes (`06fa151`, served from memory) gives the same result.
- **Repro:** any viewport (keyboard only). Seed S1 cut to its first item (`Nasi lemak ayam`, `nextId` 8), mode By item. Put focus on `Remove Nasi lemak ayam` (Tab). Hold Enter for about 700 ms (the page records `Enter:first`, then four `Enter:repeat` keydowns once the repeat delay of 520 ms has passed). Playwright: `keyboard.down("Enter")`, wait 520 ms, four more `keyboard.down("Enter")` 35 ms apart, `keyboard.up("Enter")`.
- **What changed in storage:** `items` goes from `[the one item]` to `[{"id":"i8","name":"","priceText":"","who":[]}]` and `nextId` from 8 to 9. A single Enter press (90 ms) gives `items []` and `nextId` 8. The page reads "Give every item a price to see the shares." where the clean removal reads "Add an item to see the shares." One click on the blank row's Remove returns `items []`. No money is affected.
- **Measurement:** `r3_overswallow.py` (8 repeats 40 ms apart) and `r3b_followups.py` section K (realistic hold): blank item `i8` and `nextId` 9 in both, click log `Remove Nasi lemak ayam` (detail 0) then `Add item` (detail 0). The other held-Enter cases are safe because focus lands in a text input, where Enter does nothing: middle person, last person, middle item and last item with others left, one removal each (4 of 4). A held Space on the same Remove is one removal (a button clicks on key release only).
- **Why LOW:** it needs a keyboard, one specific control (the sole item), and a key held longer than the operating system's repeat delay, which a normal press never is. The effect is one extra empty row that is undone with one click. It is on the keyboard path the spec promises (WCAG AA, keyboard usable), so it is worth closing.
- **Suggested fix (verified in memory, no project file written):** extend `swallowRepeatClicks` in `src/ui/dom.js` with a capture-phase `keydown` listener that cancels events with `event.repeat === true` (`stopPropagation` and `preventDefault`, which also stops the keypress that would click a button), and remove all three listeners at the first press that is not a repeat (a `mousedown` or `click` with `detail` of 1 or less, or a `keydown` with `repeat` false). Served from memory by `r3b_followups.py`: held Enter on the only item gives `items []`, `nextId` 8, no blank item and focus on `Add item` (R34 kept). Separate presses still work (Enter on Remove P2, Tab, Enter on the next Remove removes two rows with no pause). After a mouse Remove, a held letter key in the name field still types (`P3` to `P3aaaaaa`). A held Enter on New bill leaves the dialog open on Cancel instead of alternating open and shut. Tests to add: a held Enter on the only item's Remove (items empty, `nextId` unchanged, focus on Add item) and a held Enter on New bill. The alternative is to record it as an accepted residual with the sentences above.
